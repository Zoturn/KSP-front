# Frontend conventions (ksp-frontend)

## The generated GraphQL client is the contract

The backend is **GraphQL-only** — there is no REST API and no OpenAPI spec.

- **Never hand-write API types or operation functions.** They are generated by
  **graphql-codegen** from the backend's committed **`schema.gql`** into `src/api/generated/`.
- Generate from the **committed `schema.gql` file, never from a live server URL.**
  Introspection is disabled in production, so a URL-based config works in dev and mysteriously
  fails in CI.
- Files under `src/api/generated/` are **build output — never edit them by hand.**
  If something is wrong, fix the backend model/input and regenerate.
- Regenerate with `npm run generate:api` whenever the backend schema changes.
  A compile error after regeneration is the safety net working as designed.

## Writing queries

- Co-locate `.graphql` documents (or `gql` tags) with the feature that uses them; codegen
  produces a typed hook per operation.
- **Select only the fields the component renders.** Over-selecting silently costs backend
  work — this is the discipline GraphQL trades for its flexibility.
- Name every operation (`query ProductGrid { ... }`) — names appear in codegen output,
  server logs, and error paths.

## Errors arrive with HTTP 200

GraphQL signals application failures in an `errors` array, not via status codes.

- Never branch on HTTP status. Check `errors` and read `errors[0].extensions.code`
  (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_USER_INPUT`, `CONFLICT`).
- `data` and `errors` legitimately **coexist** — a partially successful response is normal.
  Render what resolved and surface what didn't; don't treat any error as total failure.
- Validation failures carry field messages in `extensions.validationErrors` — attach those to
  the individual form fields.
- A nullable field arriving as `null` because its resolver failed is expected; components must
  tolerate `null` relations rather than assuming presence.

## Server state vs client state

- **All server data goes through TanStack Query.** No `useEffect` + `fetch` fetching.
- Query keys are structured and stable: `['products', { page, categoryId }]`.
- Mutations invalidate the query keys they affect — don't hand-patch caches unless there's
  a reason (optimistic updates), and then explain it.
- Client-only UI state (modals, form drafts) stays in `useState`/context — not in Query.

## Money

The API returns integer **cents**. Never do currency math in floats; format once at the
display edge with `Intl.NumberFormat` using the `currency` field from the API.

## Components

- Small, focused, typed props. Prefer composition over prop explosion.
- Feature code lives in `src/features/<feature>/`; genuinely shared UI in `src/components/`.
- Handle all three states explicitly: **loading, error, empty**. An unhandled error state is
  a bug, not a nicety.

## Tailwind (the author is learning it — explain as you go)

- Utility-first: style with classes in the markup (`flex items-center gap-4 rounded-lg`)
  rather than writing custom CSS. **When you introduce an unfamiliar utility, say what it does.**
- Extract a **component**, not an `@apply` soup, when markup repeats.
- Use the design scale (`p-4`, `text-sm`, `gap-2`) — avoid arbitrary values like `p-[13px]`
  unless genuinely necessary.
- Responsive and state variants are prefixes: `md:flex-row`, `hover:bg-slate-100`,
  `disabled:opacity-50`, `dark:bg-slate-900`.
- Keep class lists readable; order roughly layout → spacing → typography → color → state.

## Import order

Enforced by **`@trivago/prettier-plugin-sort-imports`**, installed during Phase F1 scaffolding
(there's no `package.json` yet to install it into). Add to `.prettierrc`:

```json
{
  "plugins": ["@trivago/prettier-plugin-sort-imports"],
  "importOrder": [
    "^react$",
    "^react-dom",
    "^react",
    "<THIRD_PARTY_MODULES>",
    "^@/api/.*",
    "^@/features/.*",
    "^@/components/.*",
    "^@/hooks/.*",
    "^@/lib/.*",
    "^@/routes/.*",
    "^@/.*",
    "^[./]"
  ],
  "importOrderSeparation": true,
  "importOrderSortSpecifiers": true
}
```

Groups: React itself → all other third-party packages (TanStack Query, etc.) → our own path
aliases, ordered to match `src/`'s actual layers (`api` → `features` → `components` → `hooks`
→ `lib` → `routes`) → any other `@/` import not caught above → relative imports (`./`, `../`)
last. The `@/` alias must be configured in both `vite.config.ts` and `tsconfig.json` `paths`
before this does anything — it matches literal import specifiers, not resolved paths.

## Accessibility

Semantic elements first (`button`, `nav`, `label`). Every input has a label; every image has
`alt`. Interactive elements must be keyboard-reachable and show a visible focus ring.

## Teaching requirement

Pair every component with tests, and explain new React/Query/Tailwind concepts the first time
they appear. Capture durable concepts in `ksp-frontend/LEARNING/`.
